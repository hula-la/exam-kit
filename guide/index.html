AI는 정리와 실행. 나는 중요한 결정과 검증.

과제 원문 전달 → AI 초안 검토·중요한 질문 → 답변마다 복붙 → 제약·우선순위·스펙 결정 → 필요하면 HTML로 먼저 이해 → 개발/분석과 테스트 반복 → 최종 설명 갱신·제출. 요청문을 한꺼번에 붙이지 않고 각 단계에서 필요한 것만 씁니다.

버스 사례는 제약과 목표가 충돌하는 상황을 설명하는 가상 연습입니다. 특정 시험의 문제·정답을 복원하거나 다음 출제 유형을 예측하지 않습니다. 기술스택과 시간은 실제 안내에 맞추세요.

킷을 적용했다면, 한 줄씩 요청하세요

같은 작업 폴더의 지침을 읽은 AI에 필요한 문장 하나만 전달합니다. 전체 요청문을 한꺼번에 복사하지 않습니다. 파일 접근이 없는 AI에는 지침과 현재 spec/work를 먼저 전달하세요.

1. 스펙 파악
과제와 자료를 읽고 스펙 파악해줘.
2. 질문 정리
결과를 바꾸는 모호한 부분만 질문으로 정리해줘.
3. 답변 반영
이거 담당자 답변이야. 반영해줘.
(여기에 답변 원문 붙이기)
4. 설계 이해
현재 설계를 내가 검토할 수 있게 HTML로 정리해줘.
5. 개발·테스트
확정된 스펙대로 개발하고 테스트까지 진행해줘.
6. 다른 세션 리뷰
스펙과 실제 코드를 대조해 리뷰해줘. 수정하지 말고 문제·근거·영향만 보고해줘.
7. 최종 설명
최종 코드와 실제 테스트 결과를 기준으로 전체를 HTML로 정리해줘.

다른 세션: 같은 작업 폴더의 spec/work·코드를 읽게 합니다. 대화는 자동 공유되지 않는다고 가정하고, 리뷰 세션은 수정하지 않습니다. 개발 중 파일이 바뀌면 검토 시점을 표시하고 리뷰 결과를 개발 세션으로 가져와 반영합니다.

킷 없이 시작하거나 지시가 누락될 때 · 상세 첫 요청
과제 안내, 기존 지침·코드·자료, 설치 환경을 먼저 확인해 줘.
1. 목표·필수 기능·제출물·제약을 원문 위치와 함께 짧게 정리해. 기술스택 자유여도 기존 코드와 실행 가능한 환경부터 확인해.
2. 자료에 없고 답에 따라 설계·결과가 바뀌는 질문을 영향이 큰 2~3개부터 제안해. 각 질문에 달라지는 결정, 네 추천과 근거를 붙여. 이미 명시된 것은 다시 묻지 마.
3. 답 전에 확정하면 안 되는 조건과 병행 가능한 일을 나눠. 내가 결정하도록 위임된 우선순위는 대안을 비교해 주고 내가 선택하게 해.
4. 입력의 ID·단위·시간 기준·누락/중복 처리, 필수 제약, 목표 순서·동률 기준, 단순 기준 해법, 과제에 필요한 최소 결과물(UI·API가 필요하면 그 계약)을 제안해. 근거 없는 조건은 가정으로 표시해.
5. 실행·설치·데이터 접근과 필수 제출 방식의 장애를 초반에 확인해. Docker가 필수라면 사용 가능 여부를 먼저 확인하고 첫 최소 앱부터 build/run을 시도할 계획을 잡아.
6. 앞으로 답변은 받을 때마다 붙여넣을게. sources/dialogue.md에 질문·답변 원문을 그때그때 추가하고, notes/spec.md에는 현재 요구·제약·목표·미확정, notes/work.md에는 진행·실제 검증·다음 행동을 정리해. 기존 같은 역할의 파일이 있으면 재사용하고 원본은 보존해.
처음 방식만 설정하면 이후에는 새 답변과 필요한 단계별 요청문만 전달할게. 작은 답마다 새 파일을 만들거나 전체 대화를 기다리지 마.
나는 핵심 원문을 읽고 질문·우선순위를 검토해. 담당자에게 보낼 질문은 내가 보내고 답을 전달할게. 지금은 조사·초안만 진행해.
확인하지 않은 승인·실행·통과를 만들어 쓰지 마.
방향 결정 후 · 구현을 이어가기
방금 합의한 범위를 notes/spec.md에 반영하고 진행해.
과제의 작은 실제 결과부터 만들어. 알고리즘 과제면 작은 입력의 기준 해법을 실행하고, UI·API가 필요하면 입력→API→계산→결과를 연결해. 데이터·문서 과제면 계산·주장과 근거를 연결해. 생성·확정·조회가 요구되면 실제 상태 전이와 서버 권한까지 연결해.
필수 실행 방식은 첫 최소 앱에서 확인해. 실제로 못 돌린 환경은 미확인으로 남겨.
합의 범위의 구현·테스트·수정은 이어가고 매 파일마다 승인을 기다리지 마.
핵심 규칙 변경, 승인 범위 밖 외부 전송·파괴적 변경, 결과를 바꾸는 미확정 조건은 먼저 물어.
개선 전후는 같은 입력·목표·계산 시간 예산으로 비교하고, 무작위 방식이면 seed와 반복 결과도 기록해. 유효한 해 비율·목표값·실행시간을 분리해 보여 줘.
핵심 기능이 동작하면 필수 실패부터 해결해. 개선 기준이 없거나 제출 시간이 부족하면 확장을 멈춰.
notes/work.md에는 실제 명령·결과·실패·다음 행동만 짧게 갱신하고, 세부 로그는 경로로 연결해.
검증 요청 · 기대값과 실제 결과
notes/spec.md의 확정 규칙으로 검증해. 미확정 조건은 임의로 정답 처리하지 마.
반환 결과와 원자료에서 제약을 별도 로직으로 재계산하고 중복·누락·시간·정원 등 실제 요구의 위반 목록을 보여 줘. 생성 함수가 반환한 valid=true만 믿지 마.
작은 입력은 손계산 기대값 또는 가능한 범위의 완전 탐색과 비교해. 기준 해법보다 나음, 제약 충족, 전역 최적성은 별개로 보고해.
빈 입력·최솟값/경계값·잘못된 단위/ID·해를 못 찾는 조건·실제 최대 예상 규모를 위험에 맞춰 확인해. 처리시간과 실패 상태도 기록해.
UI·API 과제라면 핵심 흐름과 API 직접 호출로 권한·잘못된 입력·상태 전이·미확정 결과 노출을 확인해. 요구 변경 후 이전 후보 확정, 중복 확정·재시도, 재시작 후 유지가 필요한지도 요구에 맞춰 확인해.
실제 실행 명령·입력·기대값 근거·출력·판정·미실행을 notes/work.md에 요약하고 긴 결과는 verify/results/에 남겨. 영향 있는 변경 후 해당 검사를 다시 해.
나는 핵심 원문·기대값과 정상/실패 화면을 직접 대조할게. 테스트 개수나 화면 완성도로 정확성을 주장하지 마.
문서·분석 과제라면 모집단·분모·기간·단위·원자료와 최종 수치, 주장–근거 연결을 먼저 확인해. 과제에 없는 화면·API·알고리즘 검사를 강제하지 마.
선택 예시 · 알고리즘과 UI·API가 핵심인 버스 과제

노선 알고리즘에서 내가 결정할 것

① 반드시 지킬 조건

예: 정원, 도착 기한, 대상자 범위, 최대 탑승시간. 실제 과제와 담당자 근거가 있어야 합니다. 제약을 어긴 해는 목표 점수가 좋아도 확정하지 않습니다.

② 더 좋은 해의 기준

예: 차량 수, 총 이동시간, 최대 대기시간, 커버리지. 서로 충돌할 수 있으므로 우선순위·동률 기준을 정합니다. 숫자 가중치를 AI가 임의로 넣지 않게 합니다.

③ 어디까지 개선할지

단순한 기준 해법을 먼저 확보합니다. 작은 예시의 품질과 실제 입력 규모를 확인한 뒤 개선을 선택합니다. 같은 입력·목표·시간 예산으로 유효한 해 비율·목표값·실행시간을 비교하고, 무작위 방식이면 seed와 반복 결과를 남깁니다. 기존 최적화 패키지를 우선 확인하고, 새 설치는 품질 개선 효과와 설치·배포 비용을 비교해 결정합니다.

④ 어떤 주장을 할 수 있는지

제약 충족과 최적성은 별개입니다. 휴리스틱이 해를 못 찾았다고 불가능을 증명한 것도 아닙니다. 실제 확인한 범위까지 설명합니다.

경로·응답은 설계 예시입니다. 로그인·저장 방식·권한별 조회 범위·재시작 후 유지 필요성은 실제 요구에 맞춥니다. 확정 시 입력/규칙 버전, 이미 확정된 상태, 중복 클릭·재시도도 요구에 맞게 처리합니다. 정상 결과뿐 아니라 로딩·입력 오류·후보 없음·확정 성공도 화면에서 구분합니다.

스택 자유일 때: 기존 코드·설치 환경 → 내가 읽고 고칠 수 있는 스택 → 배포·패키지 제약 순서로 고르세요. 프론트와 백엔드를 반드시 다른 서버로 나눌 필요는 없습니다. 지도·별도 DB·새 프레임워크는 요구 충족에 필요할 때 추가합니다.

시간을 아끼는 네 가지 규칙

  • 정리와 문서는 AI가 작성. 사람은 근거와 결정만 검토합니다. 여러 대화는 원문·spec·work로 분리하고 짧은 단발 작업은 work 하나로 줄여도 됩니다.
  • 질문은 결과를 바꾸는 것부터. 답이 늦으면 원본 점검·입출력 골격처럼 영향을 받지 않는 일을 진행합니다.
  • 첫 결과를 작게, 보고를 짧게. 정상 동작이 생기면 동일 입력으로 개선 전후를 비교합니다. 불필요한 재설계·도구 설치에 오래 머물지 않습니다.
  • 검증은 위험이 큰 곳부터. 알고리즘 제약·권한·확정·필수 제출을 먼저 확인하고, 통과한 검사는 변경 영향이 있을 때 다시 실행합니다.

실제 후속 설명은 내가 직접 해야 합니다. “왜 이 우선순위인가 / 어떻게 계산하는가 / 무엇으로 확인했나 / 어디까지 확실한가”를 말할 수 있으면 됩니다.
