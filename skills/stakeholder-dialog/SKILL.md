# 담당자와의 대화

## 원칙
- 해법보다 상황을 먼저 묻는다. 상대는 바쁘고 답이 짧다. 한 번에 2~3개씩 묶고, 질문마다 왜 묻는지(어느 자료 몇 행, 안내의 어느 문장)를 붙인다.
- 초안은 참고용이다. 사용자가 자기 말로 고쳐 보내도록 권하고, 출력 끝에 "고쳐 쓸 때 꼭 남길 근거"를 한 줄 적는다. 존댓말, 짧게, 문단 2~3개.
- 상대의 답은 해석을 보태지 말고 그대로 `notes/decisions.md`에 옮긴다. 답이 없는 항목은 "가정"으로 표시하자고 제안한다. 담당자 역할이 없는 과제면 질문을 가정 후보로 바꿔 낸다.

## 상황별
1. **처음(과제를 읽은 직후)**: 지금 누가 어떻게 하는지, 얼마나 걸리는지, 최근 문제가 된 사례. 성공 기준을 숫자로(시간, 누락과 오탐 중 무엇이 더 나쁜지, 분량·형식). 결과를 누가 어디서 쓰는지, 범위 밖. 실행 환경의 제약(인터넷, 파이썬·패키지, 자료 반출).
2. **자료 점검 뒤**: 함정마다 "이렇게 보이는데 어떤 기준으로 처리할까요"에 근거를 붙인다. 코드표·단위·버전이 다르면 어느 쪽이 맞는지. 정답을 아는 예시가 있는지.
3. **합의문**: 범위, 규칙, 성공 기준, 출력 형식을 5~8줄로 적고 "이대로 진행해도 될까요"로 끝낸다.
4. **중간 결과 공유**: 결과 요약 3줄과 확인 부탁 1~2개(빠진 것, 틀린 것). 숫자는 실제 출력값만 쓴다.
5. **요구·자료 변경**: 무엇이 바뀌는지, 영향 범위, 다시 확인할 항목을 적는다. 처음부터 다시 만든(스크립트면 다시 실행한) 뒤 전후 비교를 보내겠다고 쓴다.
6. **마무리**: 결과 위치, 실행 방법, 남은 한계, 다음 확인 사항을 짧게.

## 출력
보낼 메시지 초안(사용자가 자기 말로 고쳐 보낸다), 이 메시지로 받으려는 정보 한 줄, `notes/decisions.md`에 적을 후보.
