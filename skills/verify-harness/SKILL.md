# 실제 결과를 검증하고 수정

1. 과제 원문·notes/spec.md·유효한 담당자 답/사용자 결정을 확인한다. 기대값과 근거를 먼저 정한다. 새로운 업무 기준을 임의로 테스트에 넣지 않는다.
2. 필요한 경우 verify/contract.json을 작성한다. why에 근거 위치를 넣고 파일·형식 검사는 kit/check.py로 재사용한다. 앱/API 과제는 이 도구만으로 동작을 검증할 수 없으므로 별도 실제 호출·상태·권한 검사도 한다.
3. 독립 검사는 생성 함수의 valid=true나 같은 집계 함수 재호출에 의존하지 않는다. 원자료에서 제약을 재계산하거나 작은 손계산/다른 집계/가능한 완전 탐색과 비교한다. 실제 구현을 실행해 얻은 결과를 독립적으로 검사하는 것은 허용된다.
4. 합의된 규칙 안의 검사·수정·재실행은 계속한다. 기준이 미확정이면 그 부분만 묻는다. 사용자가 직접 터미널 명령을 다시 치는 것을 의무화하지 않는다.
5. 생성 출력 재실행 시 원문·사용자 파일을 보존한다. 무조건 output/ 전체를 삭제하지 않는다. 승인 범위 밖 삭제·변경은 구체적으로 확인한다.
6. python3 kit/check.py --log를 실행하면 notes/work.md에 요약이 추가된다. 상세 결과는 verify/last_result.md에 남는다. 실패·보류·검사 0개를 통과로 보고하지 않는다. 종료 코드 0은 실행한 검사 모두 통과, 1은 실패, 2는 보류/미검증/설정 오류다.
7. 사람이 확인할 것은 기대값 근거·실제 출력·핵심 화면과 판단이다. 제약 충족, 기준 대비 개선, 전역 최적성의 확인 범위를 구분한다. 영향 있는 변경 후 필요한 검사를 다시 한다.

결과 보고: 실제 명령·입력·기대값 근거·출력·판정·미실행. 테스트 수를 늘리는 것 자체를 목표로 삼지 않는다.
