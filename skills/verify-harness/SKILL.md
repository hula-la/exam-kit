# 검증 하네스

목적: 제출 전에 누구나 한 명령으로 결과물을 점검할 수 있게 한다. 점검 기준은 과제 안내에서만 가져온다.

## 순서
1. `verify/contract.json`을 만든다. 기준은 `kit/contract.example.json`. 항목마다 과제 안내의 근거 문장을 `"why"`에 적는다. 안내에 없는 기준은 넣지 않는다. 표가 아닌 결과물(문서, JSON, 앱 출력)은 파일 존재·`contains`·`min_bytes`·`json_keys`로 적는다.
2. 실행하기 전에 계약을 사용자에게 보여 주고 확인을 받는다. 사용자가 기준을 모른 채 "통과"만 보는 일을 막기 위해서다.
3. `verify/custom_checks.py`에 **구현과 다른 경로**의 교차 검증을 1~3개 넣는다. 예: 작은 부분집합을 직접 세기, 다른 방식으로 다시 집계하기, 정답을 아는 예시 입력을 실행해 기대 출력과 대조하기, 소표본을 직접 판정해 자동 판정과 비교하기, 안내의 요구 항목이 결과물의 어디에 있는지 대조하기. 기준은 `kit/custom_checks.example.py`. 구현 코드를 다시 불러 같은 값을 얻는 것은 교차 검증이 아니다.
4. 결과물을 스크립트가 만드는 과제면 처음부터 다시 실행할 수 있게 `verify/run.sh`를 만든다(스크립트가 다시 만드는 출력만 삭제 → 스크립트 실행 → `python3 kit/check.py --log`). 삭제 범위는 실행 전에 사용자에게 보여 주고 확인받는다. 손으로 쓴 결과물만 있으면 삭제 단계 없이 check만 넣는다. 기준은 `kit/run.example.sh`. 계약의 `run`은 출력을 덮어쓰므로 사용자 확인 뒤에만 넣고, `--run`을 줄 때만 실행된다.
5. `python3 kit/check.py`를 실행해 표를 보고한다. 실패 항목은 원인과 고칠 범위를 먼저 보고하고 지시를 기다린다. 보류(판정 불가) 항목은 사용자가 직접 볼 것으로 남긴다.
6. 결과는 `verify/last_result.md`에 남고, `--log`를 주면 `notes/verification.md`에 한 줄 추가된다. `python3 kit/preview.py`로 HTML에서도 볼 수 있다.

## 지킬 것
- 점검이 통과해도 "검증 완료"라고 쓰지 않는다. "계약 점검 N/M 통과, 교차 검증 K개 일치"처럼 수치로 쓴다.
- 제출 전 마지막 실행은 사용자가 직접 한다.
