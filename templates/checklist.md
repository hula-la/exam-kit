# 진행 순서

스킬은 이 순서로 쓴다. 과제에 없는 단계(담당자, 자료 파일)는 건너뛴다.

1. 작업 폴더 루트에서 `codex`를 켠다. `/status`로 작업 폴더에 쓸 수 있는지, `/skills`에 스킬이 보이는지 확인한다.
2. `$task-brief` → `notes/brief.md`. Codex가 쓰는 동안 과제 안내를 끝까지 직접 읽는다. 다른 터미널 탭에서 `python3 kit/preview.py --serve`를 띄우고 브라우저 미리보기(출력된 포트)로 읽는다.
3. brief를 보고 `notes/requirements.md`를 내 말로 직접 채운다. AI에게 시키지 않는다. brief와 다른 점, "안내에 없음"으로 표시된 것, 빈칸이 질문 목록이다.
4. `$stakeholder-dialog` → 담당자에게 상황 질문을 한 번에 2~3개씩 내 말로 보낸다. 답이 오면 이어서 묻는다(총 개수에 상한 없음. 답이 결과를 바꾸지 않을 때 멈춘다). 담당자가 없으면 질문을 `notes/decisions.md`에 가정으로 적는다.
5. 자료 파일이 있으면 `$data-audit`(읽기 전용) → 함정에 근거를 붙여 규칙 질문.
6. `$grill-me` → 내 구현 계획을 심문받는다. 답마다 이유를 말하고, 모르면 모른다고 한다. 결정 표는 `notes/decisions.md`로, 못 답한 질문은 담당자에게.
7. 합의문(범위·규칙·성공 기준·출력 형식)을 보내 확인받고 첫 커밋.
8. 계획 검증: `$verify-harness` → 안내와 합의문에서 `verify/contract.json`을 만든다(항목마다 안내의 근거 문장). 실행 전에 내가 읽고 출처 없는 기준은 뺀다. 이 계약이 구현의 목표다.
9. 구현은 한 단위씩 맡긴다(범위, 제약, 완료 기준, 확인 방법). 결과를 직접 보고 커밋한다. 단위가 끝날 때마다 `python3 kit/check.py`를 돌려 통과가 늘어나는지 본다. 요구나 자료가 바뀌면 처음부터 다시 만들고 전후 비교를 받는다.
10. 결과 검증: 구현이 끝나면 `verify/custom_checks.py`에 구현과 다른 경로의 교차 검증을 넣고, `python3 kit/check.py --log`를 새 탭에서 내가 직접 실행한다. 실패·보류를 처리한다.
11. `$handover-docs` → 결과 문서(안내가 정한 파일명. 없으면 README.md. 안내문이 README.md면 다른 이름). 미리보기에서 수치를 대조한다.
12. 마무리: 무엇을 왜 만들었는지, 핵심 수치와 출처, 중요한 결정과 근거, 약점과 다음 검증을 내 말로 적어 둔다. 필수 파일을 확인하고 마지막 커밋.
